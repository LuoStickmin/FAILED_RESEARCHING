## 1. 口径：什么算“完全不成立”

这里只收一种结论：**有静态证据或真机实测，足以否定“靠改数据、复用现有
路径”实现目标。**

因此以下都不算：

- 缺一个外部输入、方向仍然成立的（QEMU 启动链、镜头驱动）；
- 只做到一半、关键一环没有闭环的（L 失真数据的符号歧义）；
- 已经成功的（D7200 1080p 高码率）。

按这个口径，2026 年 11 月的 8 条研究线里只有 3 条完全不成立：

| # | 研究 | 目标 | 否定证据 | 详情 |
| --- | --- | --- | --- | --- |
| 1 | **D750 TIF 存储** | 拍摄菜单增加 TIFF（RGB） | 没有 TIFF 编码器，也没有任何语言的菜单文本；只有文件名模板和 EXIF/XMP 解析表 | [01](projects/01-d750-tif.md) |
| 2 | **D750 AVI / 320×240 30i** | 增加 AVI 录像与隔行低分辨率 | 没有 AVI/RIFF 写入器、没有 MJPEG 通路、没有 320×240 或隔行模式；只有 MOV/H.264 | [02](projects/02-d750-avi.md) |
| 3 | **D7200 640×424 30p** | 复用 1080p30 档位录 640×424 | 三种改法全部真机失败：花屏条纹、录成 1080p60、仍条纹；编码器很可能没有该模式 | [03](projects/03-d7200-640x424.md) |

### “不成立”的边界

否定的是**“静态补丁 / 复用现有数据”这条路径**，不是“Nikon 永远做不到”。

- TIF、AVI 真要做，需要新写编码器/容器写入器、接采集管线、加菜单项与持久化
  —— 那是功能移植，不是改字节；
- 640×424 真要做，需要改编码器/缩放器或换一条采集路径 —— 也不是改表。

所以更准确的表述是：**在“不改代码、只改现有数据”的前提下，这三条完全不
成立。**

## 2. 三个案例

### 2.1 D750 TIF：字符串不是编码器

D750 固件里确实有 `.TIF`，但三类命中都不是“能拍 TIFF”：

- `0x126b4b6` 的 `DSC_0000.TIF` 是 DCF 文件名模板；
- `0x1bf9ec` 的 `JPG\0TIF\0` 是 XMP 元数据解析器的扩展名表；
- `0x11edf40` 的 TIFF/EXIF 标签表是**读**元数据的框架，不是像素编码器。

D810/D850/D5 也有 `DSC_0000.TIF`，而它们支持 `TIFF (RGB)`——模板是平台通用的，
不能拿来证明当前机型能写。D750 也没有任何语言的 `TIFF`/`TIF` 菜单文本。

**否定点：缺编码器 + 缺菜单文本 + 缺设置持久化。** 详见
[projects/01-d750-tif.md](projects/01-d750-tif.md)。

### 2.2 D750 AVI：能力位不是复用器

D750 的 `.AVI` 只出现在文件类型注册表里（ID 5、能力位 `0x10`）；读写函数只是
`ldrb [r0,#0x29]` / 置位，不是 AVI 复用器。

真正缺的是四层：

1. 没有 AVI/RIFF 写入器（`avih/movi/idx1/LIST/strh/strf/hdrl/00dc` 全 0 命中，
   只有 WAV 的 `RIFF` 模板）；
2. 没有 Motion-JPEG 视频通路（`MJPG`/`MJPEG` 全 0 命中），只有 MOV/H.264；
3. 没有 320×240 或隔行电影模式（只有 1080p/720p/640×424 逐行）；
4. 没有 `Movie file type` 菜单，也没有 `AVI` 菜单文本。

**否定点：缺写入器 + 缺编码路径 + 缺采集模式 + 缺菜单。** 详见
[projects/02-d750-avi.md](projects/02-d750-avi.md)。

### 2.3 D7200 640×424：三套索引空间

电影模式表里确实有 640×424 30p（第 19/20 项），映射函数也有 group 2 分支。
但三种改法全部被真机否定：

| 版本 | 改法 | 真机结果 |
| --- | --- | --- |
| v1 | 只替换表记录 | 容器 640×424 / 29.97p，时间正常，但画面规律条纹 |
| v2 | 映射函数返回原生索引 `0x12/0x13` | 录成 1920×1080 59.94p，10 s 变 4.8 s |
| v3 | v1 + scaler 尺寸字段 `0x2C46A4` | 显示 640×424，但仍条纹 |

**否定点：模式表、编码器索引、缓冲区 stride 是三套不同的索引空间；改对一套
不代表另外两套也对。** 详见
[projects/03-d7200-640x424.md](projects/03-d7200-640x424.md)。

## 3. 共同模式

三个案例看起来是三种功能，实际是同一类错误：**把“存在某个字符串/表项”当成
“存在某条功能路径”。**

判断一个需求能不能靠补丁实现，按顺序问：

1. **有没有写入器/编码器？** 扩展名、文件类型注册表、能力位都不算；
2. **有没有采集/缩放路径？** 模式表里的一行、分辨率常量都不算；
3. **有没有菜单文本 + 描述符 + 枚举 + 持久化？** 只有标签不算；
4. **有没有回放/文件系统兼容？** 只写得出文件不算；
5. **改的是数据还是代码？** 数据表里有没有现成记录可以复用；
6. **能不能用最小代价在真机上证伪？** 先刷 stealth 版，先看文件而不是菜单。

只要 1–4 里缺一层，成本就会从“改几个字节”跳到“移植一个功能”；到那一步，
“完全不成立”指的就是补丁路径，不是功能本身。

## 4. 为什么只留这三条

另外 5 条不属于这个口径，不在本仓库展开：

- 3 条被外部输入卡住（D750 QEMU、D780 QEMU、LiveView AF/镜头链路）；
- 1 条部分成立（尼康 L 失真控制数据的符号歧义）；
- 1 条真机成功（D7200 1080p 64/60 Mbps）。

它们的方向没有被否定，只是缺数据、缺硬件输入或已经交付，混进来会稀释
“完全不成立”这个判断。
